# 边界与内容净化

## 路由边界

### 使用本 skill

- 用户想发散方向、比较方案或模拟不同角色视角。
- 需求还未形成明确方案。
- 用户价值、成功标准、范围或约束不清。
- 继续实现会制造关键假设。

### 不使用本 skill

- 已有明确方案，只需要反驳和裁定。
- 需要检查代码实现、测试缺口或 bug。
- 需要审计交付、新人接手、安装流程或公开仓库体验。
- 需要安全授权、漏洞验证、攻防分析或逆向解构。
- 需要把方法论转成 skill。

## 澄清边界

- 只问 P0 阻塞项。
- 常规目标是 0-3 个问题。
- 最多 6 个问题只用于复杂高风险场景。
- 提问后必须停止等待回答。
- 无工具时输出 `ClarificationRequest`，不得编造用户回答。
- 多选题必须说明可多选，并保留“其他/不确定”出口。

## 内容净化

禁止写入交付物或 skill 规则：
- 私有路径、个人目录、真实用户名或本机专属配置。
- 凭据、密钥、令牌、cookie 或可恢复的脱敏前信息。
- 具体来源叙事、具体对话出处、外部来源链路或内部推导轨迹。
- 与当前功能无关的工具名、运行时名、私有规范名或维护说明。
- 过度承诺式表达，如把推断写成确定结论，或用覆盖性措辞替代证据。

允许保留：
- 可独立执行的流程、约束和输出格式。
- 抽象后的场景、角色、评价维度和验证方法。
- 用户明确给出的业务目标和非敏感约束。

## 隐私与效果权衡

发现潜在敏感信息时，先判断删除是否影响效果：
- 不影响效果 → 删除。
- 影响理解 → 模板化或抽象化。
- 影响验证 → 提供替代表述，并把原始信息留在待确认项中，不写入公开规则。

## 误触发规避

- “思辨一下”“反驳方案”不一定是 brainstorming；若已有明确方案，应进入方案审查。
- “多视角审一下”不一定是 brainstorming；若对象是交付路径，应进入交付审计。
- “安全审查”不属于 brainstorming。
- “把这个方法固化成 skill”不属于 brainstorming。

## 公开前检查

- skill 文件中不应出现私有路径或来源叙事。
- `SKILL.md`、`agents/interface.yaml`、`references/` 的名称和引用必须闭合。
- 公开入口、安装白名单和变更记录必须与实际公开状态一致。
- 若只是孵化状态，不应出现在公开入口。
