# 辩证自我审查 / Dialectical Self-Review

在行动之前，先成为自己的反方。

**核心区别：**
- 代码审查：审查实现、缺陷和测试缺口 → 外向·代码
- 交付审计：审查系统对新人或新环境的可用性 → 外向·系统
- 早期发散：探索多个候选方向 → 发散·创造
- **本 skill**：对自己已有的方案做结构化反驳 → **内向·收敛**

**硬约束：审查的是思考过程和方案逻辑，不是代码行。输出辩证报告 + 修正方案。**

## 路由边界

- 需求还没定、需要发散探索多个方向 → 本 skill 不处理；可另启早期发散流程
- 已有候选方案，需要行动前自我反驳并收敛 → 用本 skill
- 需要审查代码 diff、实现 bug、测试缺口 → 用代码审查流程
- 需要漏洞挖掘、渗透、授权 CTF/靶场安全审查 → 本 skill 不处理；可另启安全审查流程
- 需要模拟新人接手、交付可用性、仓库公开体验 → 本 skill 不处理；可另启交付审计流程

## 何时使用

- 在已有明确方案且即将做重要决策、提交或合并前
- 用户说「思辨一下」「对抗性审查你的思考」「先想清楚再做」
- 方案涉及不可逆操作（push、删除、架构选型、数据迁移）
- 多轮迭代后觉得「差不多了」但还没验证逻辑自洽
- 方案已有候选路径，且涉及多个互相矛盾的需求需要收敛

## 流程

```
提出方案 → 论点提取 → 证据三值 → 澄清闸门 → 反事实/反驳 → 反反驳 → 裁定 → 修正方案
   A           B           C           D           E          F        G        H
```

详见 `references/dialectic-protocol.md`。

### 步骤 A：明确当前方案

将当前方案（无论是自己提出的还是对话中形成的）清晰地陈述出来。不要模糊化。

### 步骤 B：论点提取

从方案中提取所有**隐含的假设和关键决策点**。问自己：
- 我做了哪些假设？
- 哪些决策看起来「显而易见」但其实有替代方案？
- 哪些地方我说了「应该」「必须」「显然」但没给理由？
- 是否命中 `references/known-blindspots.md` 中的权限、网络、文件系统、用户意图、环境、时间等系统性盲区？

### 步骤 C：证据三值判断

对每个论点先判证据状态，再做方案裁定：
- **支持**：有用户原话、文件事实、命令输出或明确约束支持
- **反证**：已有证据与论点冲突
- **未知**：只能推断或缺少可验证证据

证据为「未知」时，不得强行裁定为成立；只能标记待确认、保守修正或提出最小验证方式。

### 步骤 D：澄清闸门 / AskUserQuestion 支持

AskUserQuestion 是可选澄清能力，不是硬依赖。仅当以下条件同时成立时才触发：
- 缺失信息会改变行动边界、成功标准、风险接受度、不可逆动作授权或最终裁定
- 无法通过当前对话、只读文件、已有命令输出或最小验证自行确认
- 若继续推进，会制造关键假设或误导用户

触发时只问最少必要问题：
- 每轮最多 1 次澄清请求
- 最多 6 个独立短答、多选或互斥选择问题；禁止把多个无关判断合并成一个长问题
- 只问 P0 阻塞项：会改变行动边界、风险接受度、回滚路径、授权或最终裁定的问题
- P1/P2 未知不得静默丢弃，必须进入延后确认队列，标注为什么本轮不问
- 问题类型必须明确为短答、互斥选择或多选；多选题需说明可选多个选项并保留「其他/不确定」出口
- 同时给出无回答时的保守路径：停止、只读、降级或待确认

若运行环境有 AskUserQuestion / request_user_input / 等价提问工具，且该工具支持当前问题数量和多选语义，可用该工具询问；若没有或能力不足，输出 `ClarificationRequest` 文本块，不得拆成第二次追问，不得编造用户回答。

question_budget 默认值：
- max_requests_per_turn: 1
- max_questions_per_request: 6
- requires_stop_after_request: true

最多 6 个是高风险复杂场景的上限，不是常规目标；低风险任务应保持 1-3 个最少问题或不提问。

若 P0 阻塞项超过 6 个，选择最能改变行动边界的 6 个，其余列入延后确认队列；不得为了压缩到 6 个问题而继续推进高风险方案。

最小验证只允许只读动作：读取文件、查配置、查 git 状态、静态依赖搜索、无状态命令。禁止把 push、delete、migration、写数据库、状态变更请求、读取/打印真实 secret、生产写接口调用称为“最小验证”。

### 步骤 E：反事实 / 逐条反驳

对每个假设/决策，提出**「如果这是错的呢？」**：
- 有没有反例？
- 有没有用户明确说过相反的话？
- 最坏情况是什么？
- 如果一个有洁癖的人接手，他会怎么看？
- 是否有代码层面的线索支持？路径硬编码、权限缺口、竞态逻辑——若发现，记录为证据但不审查代码本身，标记为「待代码审查的思维盲区线索」
- 如果选择相反方案会怎样？
- 如果用户环境、权限、时间窗口或输入条件不同会怎样？
- 如果关键假设失效，最小损害路径是什么？

### 步骤 F：反反驳

为原方案辩护。但如果辩护不住就**老实承认**，不要强撑。
- 辩护得住 → 记录理由
- 辩护不住 → 标记「推翻」

### 步骤 G：第一性原理裁定

对争议点用基本判据链裁定。详见 `references/first-principles.md`。

行动裁定使用三值：
- **成立**：证据支持，反驳后仍站得住
- **推翻**：证据反证或反驳不可辩护
- **修正**：方向可保留，但边界、步骤、成本或验证方式需要调整

### 步骤 H：修正方案

基于裁定结果输出修正版。明确标注：
- **保持**：哪些决策经过反驳后仍然成立
- **推翻**：哪些假设被证伪
- **修正**：哪些需要调整

### 可选 Agent-assisted 模式

默认只做单体自审，保持低成本。仅在以下条件之一成立时，升级为只读 Agent-assisted 审查：
- 用户明确要求多 Agent、对抗审查、交叉审查或团队审查
- 方案涉及不可逆操作、架构迁移、安全/权限/数据边界、跨模块影响
- 自审出现 ≥2 个「推翻」或「未知」
- 单体自审无法裁定，但任务仍需要继续推进

升级时控制成本：
- quick：0 个子 Agent，仅单体自审
- standard：2 个只读子 Agent，分别审查假设漏洞和架构一致性
- deep：3 个只读子 Agent，增加复杂度/技术债审查；安全或隐私角色仅在相关时加入

Agent 结果只作为证据输入，不替代最终裁定。汇总时标注：参与角色、共识、冲突、采纳/拒绝理由。

### 递归终止判据

- 本轮审查无「推翻」项且「修正」项 ≤ 1 → 自动终止，不重复审查
- 禁止对辩证审查报告本身再次触发辩证审查——防止审查→改进→再审的无限循环
- 用户明确说「够了」→ 立即终止
- 继续审查只能重复已有观点、无法获得新证据、或下一步必须询问用户 → 停止并标记「待确认」
- 风险已降到用户目标可接受范围，继续审查收益低于成本 → 停止
- 已提出一次 AskUserQuestion/ClarificationRequest 后，等待用户回答；不要在同一轮继续追问
- 能通过上下文、文件或命令验证的问题，禁止转嫁给用户
- 涉及不可逆、迁移、权限/安全/隐私、数据边界或跨模块影响时，缺少授权、回滚或影响面任一项 → 只读审查并待确认，不进入执行

```markdown
### 待确认项

<完整的修正版方案>
```

## 相关技能

可选搭配（本 skill 完全独立，以下仅作辅助增强）：

- 方法论固化流程：辩证审查中发现可复用判断框架时，可另行沉淀
- `adversarial-successor-audit-kelen`：修正方案涉及交付时，可触发交付前审计

## 不做什么

- 不审查代码语法或逻辑（那是 code review）
- 不审查系统对新人的可用性（那是 `adversarial-successor-audit-kelen`）
- 不发散探索新方案（那是 `brainstorming`，内置 skill）
- 不把方法论固化为 skill（那是 `skill-self-evolution-kelen`，但本 skill 可触发它）
- 不做无目的的哲学讨论 — 每个论点必须有明确的「成立/推翻/修正」结论
