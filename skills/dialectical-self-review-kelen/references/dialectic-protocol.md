# 辩证协议详解 / Dialectic Protocol

## 外显推理边界

输出结论依据、证据、反例、取舍和裁定，不输出完整私密思维链。目标是让用户能审查你的判断质量，而不是暴露每一步内部推理。

可输出：
- 关键假设
- 支持或反证证据
- 反事实场景
- 裁定理由
- 修正后的行动方案

不输出：
- 冗长内心独白
- 无证据的联想链
- 为了显得严谨而重复的推理文本

## 八段协议

### A. 明确方案 — 审查对象必须具体

先把要审查的方案压缩成一段话，明确用户价值、成功标准、改动范围和不可逆点。若只能说出模糊方向，说明还在需求发散期，应转入 `brainstorming` 而不是继续辩证审查。

### B. 论点提取 — 怎样找到隐含假设

常见的假设藏匿点：

1. **「显而易见」陷阱**：你说「显然应该 X」的地方，往往有未经验证的假设
2. **「用户肯定想要」陷阱**：你推测的用户意图 vs 用户实际说的话
3. **「技术上只能这样」陷阱**：你以为没有替代方案的地方
4. **「这次不重要」陷阱**：你跳过的决策点（如命名、路径、默认值）
5. **「大家都这么做」陷阱**：你用惯例代替了思考

**提取技巧：** 把方案读一遍，对每个动词（「用 X」「放在 Y」「忽略 Z」）问一句「为什么不是别的？」

同时对照 `known-blindspots.md`，至少检查权限、网络、文件系统、用户意图、环境一致性和时间状态。

### C. 证据三值 — 先判证据，再判方案

每个论点必须先判证据状态：
- **支持**：用户原话、文件事实、命令输出或明确约束支持该论点。
- **反证**：现有证据与论点冲突。
- **未知**：只有推断，没有足够证据。

证据来源优先级：
- 用户明确要求
- 仓库文件事实
- 命令输出或工具结果
- 项目既有模式
- 合理推断
- 猜测

证据为「未知」时，行动裁定不能写「成立」。只能写「待确认」「保守修正」或提出最小验证方式。

### D. 澄清闸门 — AskUserQuestion 只是可选适配

澄清不是默认步骤。只有当缺失信息会改变行动边界、成功标准、风险接受度、不可逆动作授权或最终裁定，并且无法通过上下文、只读文件或最小验证确认时，才询问用户。

优先级：
- 先从当前对话提取
- 再读最小必要文件
- 再运行低风险只读验证
- 最后才提出 ClarificationRequest / AskUserQuestion

问题约束：
- 每轮最多 1 次澄清请求
- 最多 6 个独立问题
- 问题必须能被短答、互斥选择或多选回答；多选题需说明可选多个选项并保留“其他/不确定”出口
- 只问 P0 阻塞项：会改变行动边界、风险接受度、回滚路径、授权或最终裁定
- P1 会影响方案质量但不阻塞本轮；P2 可后续只读验证。P1/P2 必须进入延后确认队列，不得静默丢弃
- 禁止把多个无关判断合并成一个长问题来规避数量限制
- 同时给出无回答时的保守路径

question_budget 默认值：
- max_requests_per_turn: 1
- max_questions_per_request: 6
- requires_stop_after_request: true

最多 6 个是高风险复杂场景的上限，不是常规目标；低风险任务应保持 1-3 个最少问题或不提问。

若 P0 阻塞项超过 6 个，只问影响行动边界最大的 6 个，其余 P0 标记为“仍阻塞，待下一轮回答后继续确认”。不要为了满足数量上限而假装已确认。

运行环境若提供 AskUserQuestion、request_user_input 或等价工具，且支持当前问题数量和多选语义，可以使用工具发问；若没有或能力不足，输出 ClarificationRequest 文本块并停止，不得拆成第二次追问，不得编造用户回答。

不要问：
- 纯信息查询
- 低风险可逆改动
- 可通过文件、上下文或命令自行验证的不确定性
- 继续审查收益低于成本的细节

最小验证边界：
- 允许：读文件、查配置、查 git 状态、静态依赖搜索、无状态命令。
- 禁止：push、delete、migration、写数据库、状态变更请求、读取或打印真实 secret、调用生产写接口。

无回答保守路径：
- 不可逆 / 数据 / 安全权限：停止或只读。
- 跨模块影响：只读生成依赖图和影响面清单。
- 低风险可逆：降级为最小安全版本，并标注待确认。

### E. 反事实 / 反驳 — 怎样有效质疑

有效反驳要具体、可验证、有约束来源：

- 模糊反驳：「这可能有问题」→ 有效反驳：「如果用户在机器 B clone，这个路径不存在」。
- 无对比反驳：「也许应该用别的方案」→ 有效反驳：「方案 A 要改 3 个文件，方案 B 只需改 1 个且无副作用」。
- 主观反驳：「我觉得不太好」→ 有效反驳：「这违反了用户在第 3 条说的'不入库'要求」。

**反驳模板：**
```
如果 <假设> 是错的：
- 具体场景：<谁在什么时候会遇到什么问题>
- 替代方案：<另一种做法>
- 替代方案的优势：<为什么可能更好>
- 替代方案的代价：<为什么之前没选它>
```

反事实检查至少覆盖一个方向：
- 如果不做这一步，会怎样？
- 如果做相反选择，会怎样？
- 如果用户环境不同，会怎样？
- 如果关键假设失效，会怎样？
- 如果继续推进造成不可逆后果，回滚路径是什么？

### F. 反反驳 — 怎样诚实辩护

原则：**辩护得住就辩护，辩护不住就承认**。

辩护得住的标志：
- 能指出反驳的具体漏洞（「那个场景不存在，因为...」）
- 替代方案的代价大于收益
- 用户有明确的约束排除了替代方案

辩护不住的标志：
- 只能说「也有道理但我觉得还是...」（感觉 vs 逻辑）
- 替代方案确实更简单且无副作用
- 原方案违反了用户明确说过的要求

**诚实条款：承认错误不丢分，死撑才丢分。**

### G. 裁定 — 三种结论

- **成立**：原方案的假设/决策经过反驳后仍然站得住。注明理由。
- **推翻**：原假设被证伪，需要用替代方案。注明新方案。
- **修正**：原方向对但细节需要调整。注明调整内容。

### H. 修正方案 — 综合必须更好

修正方案必须比原方案或单纯反方方案更好：更符合用户目标、更少假设、更小风险、更易验证。不要只把正反意见机械拼接。

修正方案至少包含：
- 保持项
- 推翻项
- 修正项
- 下一步动作
- 仍需确认的问题

## 何时可以跳过

- 操作完全可逆且影响范围 < 1 个文件 → 通常不需要辩证审查
- 用户明确说「直接做，不用想了」→ 记录但尊重
- 纯信息查询（不涉及决策）→ 不需要
- 需求尚未形成候选方案 → 转入 `brainstorming`

## 何时停止

- 本轮没有推翻项，修正项 ≤ 1
- 继续审查只能重复已有观点
- 证据不足，下一步必须询问用户或运行验证
- 风险已降到用户目标可接受范围
- 用户明确说停止
- 已提出 ClarificationRequest / AskUserQuestion，等待用户回答
