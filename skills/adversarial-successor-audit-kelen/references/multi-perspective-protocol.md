# 多视角接替审计协议

## 目标

在交付风险跨越多个领域时，用多个独立视角审查同一交付路径，降低单一审计者的盲区。该协议不要求运行环境具备并发能力；无法并发时，按角色顺序模拟，但每个角色仍需独立产出证据包。

## 触发条件

- 用户明确要求多角色、多视角、交叉验证或并发审查。
- 改动涉及文档、脚本、权限、CI、发布入口中的两个以上领域。
- 单体审计发现严重项或多个中等项，需要复核根因和修复优先级。
- 交付结论会影响对外发布、交接、上线或回滚。

## 角色矩阵

### 新人执行者
- 目的：确认一个新接手者能否按公开说明完成第一轮操作。
- 重点：快速开始、安装、初始化、日常开发、错误提示。
- 典型证据：README 步骤、脚本存在性、命令 dry-run 结果。

### 文档维护者
- 目的：确认说明文字、目录树、链接和术语不会误导。
- 重点：目录树一致性、链接有效性、术语稳定性、步骤顺序。
- 典型证据：`git ls-files`、文档引用、章节位置。

### 自动化维护者
- 目的：确认脚本、钩子和 CI 能被人类与 AI 执行环境调用。
- 重点：非交互参数、退出码、dry-run、依赖解析、脚本路径。
- 典型证据：shell 语法检查、脚本参数、只读命令输出。

### 发布守门人
- 目的：确认公开入口和发布产物与实际仓库一致。
- 重点：入库边界、版本记录、默认安装入口、回滚和发布说明。
- 典型证据：公开说明、安装脚本、变更记录、发布清单。

### 隐私边界审查者
- 目的：确认公开文件不泄露个人路径、密钥、私有配置或实现痕迹。
- 重点：个人路径、凭据、ignored 文件、示例脱敏、公开边界。
- 典型证据：隐私扫描、`.gitignore`、示例文本。

## 调度模型

- `single_actor`：单一审计者完成默认流程。
- `sequential_simulation`：单一审计者按角色顺序模拟多视角审计。
- `parallel_review`：多个审计者并发审查，最后按本协议合并。

并发只是执行优化，不改变只读边界、证据要求或裁决规则。报告必须标注实际使用的 `execution_strategy`：真实并发、顺序模拟或单体审计。

## 三值裁定

- **成立**：证据支持该交付路径可被新人完成，且没有发现阻断风险。
- **修正**：方向可行，但存在可修复缺口；必须给出修复和复验方式。
- **推翻**：关键前提不成立，新人无法完成流程、会被误导，或风险不可接受。

不要用绝对化表述代替证据。若缺少关键证据，`待确认` 只能作为证据状态；最终交付裁定仍必须落到「修正」或「推翻」，不要写「成立」。

## 交叉合并

1. 收集每个角色的三值结论、证据和修复建议。
2. 合并同类问题，保留最高严重度。
3. 对冲突结论按证据优先级裁决：命令输出 > 文件事实 > 用户明确约束 > 合理推断。
4. 任一 P0 推翻项成立时，总结论不得为可交付。
5. 对剩余 P0/P1 给出复验顺序；无法复验时标记待确认。

## 交叉通信

每个角色提交证据包：

```text
claim: <判断>
evidence: <文件事实、命令输出或明确缺口>
risk: <阻断或误导场景>
fix: <最小修复措施>
retest: <复验方式>
```

其他角色只能基于证据包提出挑战：
- 补证：要求补充文件事实或只读命令输出。
- 反证：指出证据与结论不一致。
- 合并：确认同类问题可归并为一项。
- 撤回：承认原判断缺少证据，降级为待确认。

冲突账本至少记录冲突事项、相关角色、证据等级、采纳结论、待确认点。

## 输出要求

- 角色结论必须短而具体，不写长篇心理过程。
- 每条发现必须有场景、证据、三值结论、修复措施和复验方式。
- 汇总必须说明共识、冲突、采纳理由和残余风险。
- 汇总必须说明修复闭环状态：仅给出建议、已由外部修复、已复验/再审计、仍待确认。
- 不修改文件，不执行写操作，不替代代码审查或安全漏洞验证。
