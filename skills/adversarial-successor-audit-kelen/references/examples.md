# 抽象案例：三层架构项目的迭代审计

## 背景

一个多人协作仓库需要建立可交接的 AI 协作规则、Git 工作流和自动化脚本。

## 审计轮次与发现

### 第一轮：全私有方案

**设计：** 所有规则/脚本/文档放入本地私有目录（git-ignored）。

**发现 #1 [严重] Bootstrap 死循环：**
- 初始化命令指向本地私有目录中的脚本
- 本地私有目录被 git-ignored
- clone 后 `bun run setup` → `No such file or directory`

**发现 #2 [严重] AI 入口缺失：**
- 宿主入口规则文件全部 git-ignored
- 新 AI 工具打开仓库看不到任何规则

**修正：** 采用两层架构 — 项目骨架入库 + 个人层私有。

### 第二轮：两层架构修正后

**发现 #3 [中等] 废弃残留：**
- 本地私有目录中残留多个旧版文件
- 新人会被困惑「哪个是真的」

**发现 #4 [中等] .gitignore 注释过时：**
- 注释说「自动化脚本本地私有」但脚本已入库

**修正：** 清理残留、更新注释。

### 第三轮：新人全流程模拟

**发现 #5 [中等] 宿主入口规则缺快速开始：**
- 直接从开发铁律讲起，新人不知道「我该先干什么」

**发现 #6 [严重] 交互脚本对 AI 不可用：**
- `sync.sh` / `commit.sh` 用 `read` / `select` 交互
- AI 工具无 stdin，脚本会阻塞

**修正：** 加快速开始段落、全部脚本支持非交互参数。

## 总结

三轮审计共发现 6 个问题（3 严重 + 2 中等 + 1 轻微），每轮修正后再审都能发现新的遗漏。这验证了「对抗性接替者审计」的核心价值：**不是一次性的，而是迭代式的，每轮修正后都值得再走一遍。**
