# 对抗性接替者审计 / Adversarial Successor Audit

以严格的新接手者视角，从缺少额外背景说明的状态开始走完整体流程，识别会阻断或误导接手流程的风险。

**硬约束：审计只读，不修改任何文件。输出审计报告 + 修正建议。**

## 何时使用

- 一批改动准备提交前（尤其是涉及文档/脚本/工作流/CI 的改动）
- 项目交付前、交接前
- 工作流重构后、新增自动化脚本后、接入新 AI 工具后
- 用户明确要求多角色、多视角、交叉验证或并发审查

## 审计模式

- **single**：默认模式。一个审计者按完整流程走查，适合普通提交前检查。
- **multi_perspective**：多视角模式。高风险交付、跨文档/脚本/权限/发布入口改动，或用户明确要求交叉审查时启用。

多视角模式仍是只读审计；如果运行环境支持真实多 agent，可并发执行各角色；如果不能并发，就由同一审计者按角色顺序模拟，并在报告中标注 `execution_strategy`，不降低结论标注要求。

选择模式：
- 普通提交、单一文档或单一脚本检查 → 默认 `single`。
- 跨两个以上领域、影响发布/交接/回滚，或用户要求交叉验证 → 使用 `multi_perspective`。
- 只涉及文档 → 可裁剪为新人执行者 + 文档维护者。
- 涉及脚本或工作流 → 可裁剪为新人执行者 + 自动化维护者 + 隐私边界审查者。
- 涉及发布入口 → 使用默认五角色。

## 流程

### 1. 确定审计范围

从用户上下文确定：
- 要审计的项目根目录
- 改动范围（全量 or 增量 diff）
- 交付物类型（仓库规则？自动化脚本？CI？文档？）

### 2. 模拟全流程

**以新人身份**，依次模拟以下步骤（每一步都检查 `references/audit-checklist.md`）：

```
clone → README → 安装依赖 → 初始化(setup) → 日常开发 → 提交 → 同步上游 → 合并 → 发布
```

每一步问自己：
- 我知道该做什么吗？（文档是否指引清晰）
- 命令能跑通吗？（依赖是否齐全、路径是否正确）
- 出错时有提示吗？（报错信息是否有用）
- 我会不会走歪？（有没有护栏防误操作）

### 3. 多视角接替审计（按需）

当启用 `multi_perspective` 时，按角色拆分只读审计面。每个角色独立输出三值结论：
- **成立**：当前交付路径有证据支持，按新人视角可完成。
- **修正**：方向可行，但存在文档缺口、脚本兼容性、边界不清或验证不足。
- **推翻**：关键前提不成立，新人无法完成流程或会被误导。

建议角色：
- **新人执行者**：从零开始读 README、安装、初始化、运行日常命令。
- **文档维护者**：检查术语、步骤、目录树、链接、错误提示是否一致。
- **自动化维护者**：检查脚本、钩子、CI、非交互参数、退出码和 dry-run。
- **发布守门人**：检查公开入口、入库边界、版本记录、发布产物和回滚路径。
- **隐私边界审查者**：检查本机路径、密钥、个人配置、被忽略文件和示例脱敏。

每个角色必须给出：
- 作用：该角色审查什么用户价值
- 证据：文件事实、命令输出或明确缺口
- 三值结论：成立 / 修正 / 推翻
- 漏洞：会让新人卡住或误判的点
- 修复措施：最小可执行修复
- 复验方式：如何证明已修复

最小报告格式：

```markdown
- <角色>：<成立 / 修正 / 推翻> — 证据：<文件或命令> — 风险：<一句话> — 修复：<最小动作> — 复验：<检查方式>
```

结论映射：
- 「推翻」约等于严重/P0：关键前提不成立或存在不可接受的阻断项。
- 「修正」约等于中等或轻微/P1-P2：方向可行，但需要修复或补证。
- 「待确认」不是第四种结论，只表示证据状态；最终交付裁定只能是「成立 / 修正 / 推翻」。证据不足时不得裁为成立，默认落到「修正」或「推翻」并说明补证路径。

### 4. 交叉合并与收敛

汇总所有角色结论，按以下规则裁决：
- 任一角色给出「推翻」且证据成立 → 总结论不得写「可交付」。
- 多个角色对同一事项冲突 → 标为「待裁决」，优先采用有文件事实或命令输出的结论。
- 只有「修正」无「推翻」 → 给出最小修复清单和复验顺序。
- 没有「推翻」且所有 P0/P1 风险有复验路径 → 标为「事实充分置信」；不要用无风险表述代替证据。

收敛循环：
1. 识别 P0/P1 残余风险。
2. 提出最小修复措施。
3. 给出复验命令或只读检查方法。
4. 若仍有无法验证的关键前提，标记为「待确认」，不得提升为可交付。

修复闭环定义：本 skill 不直接修改文件；闭环为「审计发现 → 最小修复建议 → 用户或修复流程实施 → 复验/再审计 → 残余风险裁定」。如果未完成复验/再审计，只能声明“修复建议已给出”，不能声明“风险已关闭”。

交叉通信只基于证据包进行：`claim / evidence / risk / fix / retest`。其他角色只能提出补证、反证、合并或撤回，不用身份设定代替证据。

### 5. 子模式检测

对每个发现的问题，用子模式深入诊断：

**子模式 A — Bootstrap 死循环检测**
> 生成物是否依赖生成器，而生成器本身也未入库？
> 判据：`git clone` 后能否在不依赖任何 git-ignored 文件的情况下完成初始化？
> Dry-Run 验证：不强求真实执行 clone+install，但需解析 install.sh / package.json / requirements.txt 检测所有外部依赖的可解析性（至少检查包名是否存在）。标注「dry-run 验证通过」vs「需要真实环境验证」。

**子模式 B — 入库边界三层判据**
> 每个文件是否放对了位置？
> - 客观项目规范 → 必须入库
> - 自动化工具 → 必须入库
> - 个人偏好/隐私 → 不入库，本地生成

**子模式 C — AI 可调用性检验**
> 每个交互式脚本能否在无 stdin 环境下使用？
> 判据：是否支持 `--yes` / `--type=` 等非交互参数？

**子模式 D — 提交内容隐私扫描**
> 入库文件中是否包含个人路径、密钥、硬编码主机名等隐私信息？
> 标准化扫描命令集见 `references/sub-patterns.md` 子模式 D。

**子模式 E — 目录树一致性检验**
> Readme.md 目录结构树是否与 `git ls-files` 实际内容严格对应？

详见 `references/sub-patterns.md`。

### 6. 输出审计报告

格式：

以下为模板，<...> 标记需替换为实际内容。

```markdown
# 对抗性接替者审计报告

## 审计范围
<项目 / 改动范围 / 日期>

## 发现

### [严重] #1: <问题标题>
- **场景**: 新人在 <哪一步> 会遇到 <什么问题>
- **根因**: <Bootstrap 死循环 / 入库边界错误 / AI 不可调用 / 文档缺失 / ...>
- **修正建议**: <具体操作>
- **验证方式**: <如何确认已修复>

### [中等] #2: ...

### [轻微] #3: ...

## 多视角汇总
- 新人执行者：成立 / 修正 / 推翻 — <证据摘要>
- 文档维护者：成立 / 修正 / 推翻 — <证据摘要>
- 自动化维护者：成立 / 修正 / 推翻 — <证据摘要>
- 发布守门人：成立 / 修正 / 推翻 — <证据摘要>
- 隐私边界审查者：成立 / 修正 / 推翻 — <证据摘要>

## 交叉裁决
- 共识：<所有角色一致的判断>
- 冲突：<角色之间不同结论 + 证据优先级>
- 采纳：<最终采用的判断和理由>
- 残余风险：<仍未验证的 P0/P1>
- 复验顺序：<先修什么、再验证什么>

## 总结
- 严重: N 项
- 中等: N 项
- 轻微: N 项
- 结论: <可交付 / 需修正后交付 / 不可交付>

结论判定默认阈值（可由用户覆写）：
- 严重项 ≥ 1 → 不可交付
- 严重项 = 0 且中等项 ≥ 3 → 需修正后交付
- 其余 → 可交付
```

## 不做什么

- 不审查代码逻辑正确性；如需此类判断，应另启代码审查流程
- 不审视觉、产品交互或界面设计质量；仍审 README、安装反馈、错误提示和新人接手路径体验
- 不修改任何文件（只读审计）
- 不做性能分析
