# 技能自我进化 / Skill Self-Evolution

本 skill 的主要作用是管理 skill 的生命周期：创建、设计、维护、迭代、改进和进化 skill，并把同一套机制应用到自身。对话方法论沉淀只是入口之一，不是全部目的。

思辨、对抗审查、多视角模拟、三值裁定、澄清问题、触发覆盖和能力等价验证，都是为了让生命周期处理更稳定、更周全、更可验证的质量机制；它们不是本 skill 的主目标。

**核心区别：**
- 历史复盘：事后挖掘旧对话或日志，产出知识笔记
- 被动记录：保存事实、偏好或一次性经验
- 普通创建：生命周期中的轻量创建分支；只把明确需求写成一个新 skill，不扩展为方法论进化
- 普通维护：只按用户指定改一个文件或修一个字段
- 审查工具：只找问题，不负责把修复进入生命周期闭环
- **本 skill**：把新建、设计、维护、迭代、改进、进化、自我修正纳入同一生命周期闭环，输出可执行修改、验证证据和残余风险
- **自我适用**：当用户要求审查、改进或证明某个已有 skill 是否达到设计目的时，本 skill 先作为上游守门流程，输出需求覆盖、缺口、修复顺序和验证路径

**硬约束：生命周期内的每一次新增或改动，都必须先证明它服务于 skill 的独立可用性、触发有效性、维护性或验证闭环；不能只增加概念或堆砌能力名。**

质量维度门禁：审查、维护、迭代、改进或自我进化 skill 时，必须逐项检查收敛、约束、稳定、通用性、兼容性、解耦性、扩展性和独立性；不要求每项都新增规则，但必须说明“已覆盖 / 需修正 / 不适用”。

## 何时使用

- 用户要求创建、设计、维护、迭代、改进或进化 skill
- 已有 skill 迭代、已有 skill 改进或已有 skill 自我进化请求
- 用户要求把某个流程、判断方法或工作方式转成 skill
- 深度对话接近尾声，准备提交/收工前
- 用户说「思辨你学到了什么」「这次对话有什么可以变成技能的」
- 多轮迭代中发现了一个反复使用的模式（如同一个判断框架被用了 3 次以上）
- 用户明确教导了一种思维方式并要求固化
- 用户要求改进、审查或迭代已有 skill，尤其是要求确认“设计目的是否真正落实”
- 用户怀疑过往 skill 改动只停留在文本层，需要按优先级逐个审查需求、实现和验证闭环
- 经本 skill 创建或迭代的下游 skill 暴露边界、隐私、交互工具调用或验证缺陷，需要把缺陷回流审查本 skill 的设计门禁
- 用户指出应出现交互式选项或澄清窗口却只收到文字选项，需要修复宿主能力适配与真实行为验证

- 审查这个 skill 有没有达到目的；改进这个 skill 的触发和效果；按优先级逐个审查 skill。

## 六段生命周期协议

```
识别任务类型 → 思辨/澄清/调研 → 第一性原理判断 → 创建/维护/迭代 → 行为验证 → 部署/发布验证
      ①               ②                 ③               ④             ⑤             ⑥
```

### 步骤 ① 识别：判定 skill 生命周期任务类型

先判断当前请求属于哪类生命周期任务：

- **创建**：从明确需求、可复用方法论或稳定工作流生成新 skill。
- **设计**：确定 skill 目的、边界、触发、输出契约、文件结构和验证方式。
- **维护**：修复现有 skill 的触发、文档、接口、验证、发布入口或隐私边界。
- **迭代**：在不破坏独立性的前提下增强已有 skill 的能力、覆盖面或稳定性。
- **改进**：针对已暴露问题做最小修复，并证明修复确实改变行为。
- **进化**：把反复出现且具备复用价值的方法论沉淀为新 skill 或合入已有 skill。
- **自我进化**：目标是本 skill 时，用同一流程审查自身目的、结构、触发和验证闭环。

若任务来自当前对话中的方法论，再补充提炼维度：

- **思维层面**：我在这次对话中是否使用了一种之前不具备的思考方式？
- **推理层面**：我是否学到了一种新的判断/决策框架？
- **方法层面**：我是否形成了一个可重复的工作流程？
- **逻辑层面**：我是否发现了一种新的论证结构或错误检测模式？

**提取模板：**
以下为模板，<...> 标记需替换为实际内容。
```markdown
### 候选方法论 N: <名称>
- 来源：对话中的哪个环节
- 定义：一句话描述
- 触发证据摘要：默认写“本轮对话/某类场景”，不写私有路径、具体人名、未授权项目名或具体来源链路
- 输入：什么情况下触发
- 输出：产出什么
- 流程：几个步骤
- 本次使用次数：N 次
```

### 步骤 ② 前置协议：思辨、澄清、调研、决策准备

在进入判断和写文件前，先用轻量协议把问题问清楚、证据找足、反方风险摆出来。低风险、目标清楚的小改动可压缩执行，但报告中仍要写明“简化执行”。

#### ②-1 澄清门槛

出现以下任一不确定性时，先澄清，再执行：
- 用户目标不清：创建、维护、改进、进化、自我进化之间无法判定。
- 目标运行时不清：不知道产物给哪个宿主或公开入口使用。
- 发布范围不清：不确定是本地孵化、公开发布、仅研发记录还是安装同步。
- 写入边界不清：不确定是否允许修改文件、同步安装、更新 README 或验证脚本。
- 隐私边界不清：可能暴露来源链路、私有路径、研发灵感或未授权项目名。

澄清规则：
- 每轮最多 1 次澄清请求。
- 每次最多 6 个问题，支持多选。
- 优先问会影响执行方向的问题；可用合理默认值解决的细节写入假设，不阻塞。

交互呈现规则：
- 需要用户回答澄清、授权或裁定选项时，先检查当前宿主是否暴露支持相应题型的交互式提问或选择能力。
- 本轮工具目录或宿主接口暴露支持题型的原生交互能力时，必须先实际调用该能力，不得只用文本列出选项冒充交互完成。
- 单选或多选候选需要 AI 给出倾向时，必须标注推荐项；每个选项必须附一句核心逻辑理由或取舍影响。单选只推荐 1 项，多选可推荐一组组合；证据不足时不强行推荐，改为说明缺口。
- 仅当原生能力未暴露，或实际调用返回不可用、拒绝、题型/题量不支持等可观察证据时，才输出单个 `ClarificationRequest` 或决策文本降级；记录 `interaction_mode: text_fallback`、`native_tool_candidate`、`native_tool_status`、`fallback_reason` 与 `capability_evidence`。
- 不依据未经实测的模式或权限推断预先跳过原生交互调用；执行访问权限和原生交互能力分别判定。
- 文字选项已输出不等于原生工具已调用；真实行为验证必须区分 `native_tool`、`text_fallback` 与 `not_needed`。

#### ②-2 证据调研

调研必须服务于决策，不做无边界搜集。按任务类型读取最小证据集：
- 用户原始需求：确认用户价值、验收标准和禁止事项。
- 具体使用例：创建或重构 skill 前，优先收集或生成 2-3 个真实触发例、近邻例或负例，用来确认 recurring job、输入、输出和不做什么。
- 目标 skill 当前文件：至少读取 `SKILL.md`，涉及接口时读取 `agents/interface.yaml`。
- 公开入口：涉及触发或新用户路径时读取 README、安装入口和触发说明。
- 验证门禁：涉及完成声明时读取验证脚本或目标环境等价门禁。
- 近邻 skill 或流程：涉及误触发、重叠或替代时读取相关边界说明。
- 参考对照：用户提供参考对象、声称融合/替代，或本 skill 自审后被用户/参考对象发现新缺口时，必须读取 1-3 个相关参考对象并做能力差异审查；不得在未对照时写“无优化点”。
- 研发文档：只在需要记录来源、纠偏或决策依据时写入；不把研发来源写进 skill 规则。
- 宿主交互能力：目标 skill 会向用户澄清、请求授权或提交裁定选项时，读取 `references/host-interaction-adaptation.md` 并规划原生工具调用与降级验证。

证据状态写法：已读 / 未读 / 不适用。若关键证据未读，不得声明“已落实”。

#### ②-3 思辨审查

在高风险、自我进化、用户质疑“是否真的落实”、融合替代效果、公开发布前启用。输出最小五项：
- 主张：本次要新增、修改或保持什么。
- 反方质疑：为什么这个改动可能无效、过度设计、误触发或偏离主职责。
- 证据：来自文件、验证、用户原话或运行结果的支撑。
- 裁定：成立 / 修正 / 推翻；`待确认` 只能是证据状态。
- 修复与复验：最小修复动作和证明方式。

#### ②-4 决策准备

进入用户决策前，每个选项必须附带：
- 依据证据：为什么可行。
- 反方风险：哪里可能失败。
- 复验方式：如何证明不是只改了文字。
- 推荐标识：单选只标 1 个推荐项；多选可标推荐组合；推荐必须来自证据、风险和复验成本的综合判断。

### 步骤 ③ 判断：第一性原理式生命周期 4 层验证

先问 skill 为什么必须存在或被改动，再问边界、结构和验证。对每个候选创建、维护或迭代动作逐层检验（方法论沉淀详见 `references/evolution-criteria.md`）：

1. **目的必要性** — 该动作是否直接服务于 skill 创建、设计、维护、迭代、改进或进化？若只是灵感记录、堆概念或一次性偏好，不进入 skill 文件。
2. **边界唯一性** — 现有 skill 或当前 skill 内部结构能否覆盖？若能覆盖，优先迭代现有能力；若边界不同，再创建新 skill。
3. **结构可执行性** — 是否能落成触发、输入、输出、流程、边界和验证？不能结构化则先待观察或写入研发文档。
4. **验证收益比** — 是否能用正例、近邻例、负例、结构检查或真实运行证据证明效果？
   - 本次已复用 ≥ 3 次（客观事实）→ 直接通过
   - 预期复用 ≥ 3 次（推测）→ 降级为「待观察」，记录在输出报告中；等实际复用 ≥ 3 次后重新触发评估
   - 用户明确要求「把这个变成 skill」→ 跳过投入产出比判断，直接通过（但仍需通过前 3 层）

**4 层全通过 → 转化为新 skill 或迭代现有 skill**
**某层不通过 → 记录在本次输出报告的「待观察」或「跳过」原因中，不写入工具特定笔记系统**

跨切面设计门禁：
- **质量维度门禁**：收敛检查是否避免无限展开；约束检查是否有硬边界；稳定检查是否有行为复验；通用性和兼容性检查是否脱离单一项目/宿主；解耦性和独立性检查是否移除非必要依赖；扩展性检查是否允许后续按 SemVer 增量演进。
- **执行自由度裁定**：先判断目标能力应保留高自由度规则、中自由度流程模板，还是低自由度脚本/强门禁；不得把需要确定性的任务只写成宽泛建议，也不得把需要判断弹性的任务过度脚本化。
- **脚本适配裁定**：遇到重复、确定性、格式严格、可自动验证或易漏检查的任务，必须判断是否应使用 `scripts/`；不创建脚本时说明原因，不把可自动验证的质量要求只留在文字规则里。
- **内容与存储边界**：运行生成的真实会话、项目记录、附件、提示内容或隐私信息不得写入可公开复用的 skill 规则目录；应由目标项目私有交付区承载。
- **宿主能力边界**：依赖交互弹窗、会话指标、安装路径或专用工具时，必须设计能力探测、等价降级与真实环境复验；不得把单一宿主能力写成通用事实。
- **自动演化边界**：子 skill 可以输出改进候选，但不得在执行其业务职责时自动改写自身规则或追加真实执行历史。
- **硬编码边界**：项目特定服务、数据库、安全扫描、路径或命令仅在功能本身必需且有适配层时出现；不得混入通用 skill 主流程。

### 步骤 ④ 执行：创建、维护或迭代（单层决策，一次性呈现）

**硬约束：呈现完整决策信息后必须等待用户回复，不可自行跳过或决定。**

对每个通过 4 层验证的方法论，一次性呈现所有决策信息：

以下为模板，<...> 标记需替换为实际内容。

```markdown
### 候选方法论: <名称>
- 定义：<一句话描述>
- 影响范围：<涉及哪些现有 skill / 新增什么能力>

决策选项：
[1] 独立转化 → 创建新 skill `<skill-name>`
    - 推荐名称：<按目标运行时或目标仓库命名规范给出>
    - 目录结构：SKILL.md + references/；目标运行时需要时可补接口声明
    - description 稿：<用户自然口语 + AI 推理触发 + 关键词 + 误触发边界>
    - 依据证据 / 反方风险 / 复验方式：<简述>
[2] 合入现有 → <推荐合入哪个 skill + 理由>
    - 依据证据 / 反方风险 / 复验方式：<简述>
[3] 跳过 → <跳过原因>
    - 依据证据 / 反方风险 / 复验方式：<简述>
[4] AI 思辨建议 → <针对此方法论的具体建议>
    - 依据证据 / 反方风险 / 复验方式：<简述>
[N] 补充说明（请描述你的想法）

⚠️ AI 推荐：[1/2/3/4]（默认推荐，用户可覆写）
```

用户回复后直接进入执行阶段（不设中间层）。若用户选择的选项信息不足，可在同一轮对话中追问细节。

自我适用规则：
- 当目标是审查或改进本 skill，自身规则同样适用；先列出用户原始目的、现有实现证据、缺口、三值裁定和最小修复顺序。
- 当用户要求审查一组 skill，先按依赖关系排序；上游方法论和验证门禁优先于单个业务 skill。
- 当请求只是普通创建一个新 skill，仍先进入本 skill 判定为 `创建`，随后走轻量创建分支；无需执行方法论沉淀筛选，也不得绕开生命周期入口。
- 当请求是“改进已有 skill 的触发、解耦、验证、边界或效果”，不得只按普通创建流程处理；必须先执行本流程的需求覆盖审查。
- 当用户要求融合、借鉴或替代某个既有流程的效果，必须读取 `references/capability-equivalence-protocol.md`，把目标抽象成能力项并给出等价矩阵；不能只写“已融合”。
- 递归终止：一次自我进化只处理当前用户目的下的 P0/P1 缺口；新发现但不阻断本轮目的的问题写入 `improvement_candidate` 或待观察，不继续展开第二轮自我进化。

**执行前预检查（写入文件前必须执行）：**
- 名称一致性检查：确认路由规则中的 skill 名称、工作空间目录名、SKILL.md name 字段三者一致 → 不一致则提示并修正后再写入

#### 路径 1：创建新 skill

1. 在当前工作空间的 skill 产物目录创建 `<skill-name>-kelen/`；`-kelen` 是本仓库默认命名约定，若目标运行时或用户命名规范不同，按目标规范生成并记录理由。
2. 示例驱动准备：写文件前先用 2-3 个具体使用例确认 recurring job、真实输入、目标输出和近邻排除项；示例不足且会影响边界时，先澄清或生成待用户确认的候选例。
3. 资源边界裁定：从具体使用例反推 `references/`、`scripts/`、`assets/`、`evals/` 或 `reports/` 是否真的必要；没有当前复用、验证或执行收益的目录不创建。
4. 按以下结构组织：
   - `SKILL.md`：路由 + 流程骨架
     - frontmatter 必含 `name`、`description`（触发场景）、`metadata`（author/version）
     - description 字段精确描述触发场景（路由匹配核心），包含用户口语触发词 + AI 自我思考触发词
     - 流程步骤保持最小化，详细内容引用 `references/`
   - `references/`：详解、判据、案例；只放触发后才需要的内容
   - 接口声明：目标运行时需要时创建，不作为通用核心结构的硬要求
   - `scripts/`：仅在输入确定、逻辑固定、输出结构化时创建
   - `evals/` 或 `reports/`：仅在需要行为评估或发布证据时创建
5. **必须读取 `references/skill-design-principles.md` 与 `references/trigger-coverage-matrix.md`**，确保新 skill 遵循格式规范、内容净化、模块独立原则和触发覆盖矩阵。
6. 新 skill 涉及澄清、授权或裁定选择时，必须读取 `references/host-interaction-adaptation.md`，声明原生交互调用优先级、文本降级条件和真实宿主验证样例。
7. 新 skill 会生成运行记录、会话材料或附件时，必须证明公共 skill 内容与私有运行产物已解耦，并阻止自动自改。

#### 路径 2：迭代现有 skill

1. 读取现有 skill 的 SKILL.md。
2. 识别增量：新流程步骤？新参考文档？新案例？新验证门禁？
3. 对照用户目的：原始意图、当前实现、未覆盖场景、误触发风险、真实验证缺口。
4. 若用户要求融合或替代某能力，读取 `references/capability-equivalence-protocol.md`，输出能力等价矩阵。
5. 先给三值裁定：成立 / 修正 / 推翻；只要存在未验证的 P0 目标，就不能写“已达成”。
6. 最小化修改，不破坏现有结构。
7. 版本号按 SemVer 裁定：修错、触发补强或文案边界微调 → patch；新增能力、公开入口或输出契约 → minor；破坏兼容或移除能力 → major 并先征求用户确认。
8. 若修改触发语义、输出契约、目录结构或验证逻辑，同步更新对应的外部发布说明与验证门禁。

#### 路径 3：维护现有 skill

1. 明确维护对象：文档入口、接口声明、引用闭合、安装入口、验证脚本、版本或隐私边界。
2. 只修复偏离当前规范或已过时的内容；不借维护名义新增能力。
3. 对公开入口做一致性检查：README、安装白名单、触发词、目录树和变更记录。
4. 若维护涉及本地同步脚本或宿主路径，保持 ignored 或本地化，不进入公开 skill 规则。

#### 路径 4：改进现有 skill

1. 先写清已暴露问题：触发不准、边界不清、执行链缺失、验证不足或用户体验断点。
2. 对每个问题给三值裁定：成立 / 修正 / 推翻。
3. 做最小行为改动；避免只加抽象词或无执行价值的描述。
4. 补正例、近邻例、负例或验证脚本门禁，证明行为确实变化。
5. 若问题暴露于本 skill 先前创建或迭代的下游 skill，同时审查是哪一项上游门禁缺失，并对本 skill 做最小自我修正。

#### 路径 5：自我进化

1. 把本 skill 当作目标 skill，先执行步骤 ② 的澄清、调研和思辨审查。
2. 检查主职责是否仍是 skill 生命周期进化，而不是被思辨、审查、头脑风暴或普通创建流程抢占。
3. 修复后只同步受影响的自身触发、接口、eval prompts、README、验证脚本或研发记录；未受影响项记录“不适用”，不得为了完整感扩大改动范围。
4. 明确结论：静态文件覆盖、当前会话按规则执行、新会话真实触发是否已验证。
5. 若缺陷来自下游 skill 的真实表现，必须将其转化为可复验的设计门禁或回归样例，而不是只修下游文件。
6. 若本 skill 曾判定“无优化点”，但后续用户指导、参考对照或实际运行发现有效改进，必须把前次自审标为未完全成功，并新增回归样例或门禁。
7. 本轮修复完成后停止；除非用户明确要求继续扩展，否则不得把新发现的改进候选继续展开为同轮自我进化。

#### 路径 6：跳过

记录跳过原因，不产出任何文件；若未来实际复用 ≥ 3 次，再重新评估。

### 步骤 ⑤ 行为验证

转化或迭代后，先证明 skill 会改变行为，再声明完成。验证应使用可迁移的正例、近邻例、负例和必要的对照样本，不依赖特定外部工具或查看器。

最小验证包：
- 正例：用户明确要求把当前方法论变成 skill → 应触发本 skill 并输出候选方法论与 4 层判据。
- 正例：用户要求审查或改进已有 skill 是否达到设计目的 → 应触发本 skill 并输出需求覆盖、证据、缺口和修复顺序。
- 正例：用户要求按优先级逐个审查过往 skill 改动是否落实 → 应先审上游方法论和验证门禁，再审业务 skill。
- 正例：用户要求维护或改进现有 skill → 应输出维护/改进对象、问题证据、最小修复和复验方式。
- 正例：用户要求本 skill 自我进化 → 应触发自我进化路径，并证明主职责没有偏离。
- 正例：用户只是要创建一个普通 skill → 应先触发本 skill 并判为 `创建`，随后走轻量创建分支，不强行做“会话领悟”筛选。
- 负例：只是项目偏好、一次性配置或会议总结 → 应跳过或列入待观察，不创建 skill。

验证层级：
- 结构验证：目录、frontmatter、`name` 字段、references 引用、公开说明、变更记录和安装入口一致。
- 触发验证：用用户自然口语、AI 自触发、近邻误触发和负例检查 description 是否可召回。
- 行为验证：用 2-3 个真实提示检查触发、跳过和边界，不把规则存在等同于行为变化。
- 前向测试：复杂、高风险或公开复用的 skill，应在新上下文或独立执行环境中用少提示测试；不得向测试者泄露预期答案、修复意图或作者结论。
- 能力等价验证：若声称融合或替代某流程效果，必须证明目标能力在触发、流程、输出、边界和验证上均有覆盖。
- 交互能力验证：包含澄清、授权或裁定选项的 skill，必须验证暴露可用候选时先实际调用原生能力；只有未暴露或调用产生可观察失败证据时才文本降级，并记录 `interaction_mode`、候选工具、状态与证据来源。
- 产物隔离验证：生成会话、附件或执行历史的 skill，必须验证真实运行数据不进入可公开复用的规则目录，且不存在业务执行期间自动自改。
- 对照验证：高风险或生产级 skill 可做 with-skill / baseline 对照；低风险改动只需人工回归提示。
- 用户反馈：输出候选方案、验证结果和残余风险，让用户决定创建、合入、跳过或待观察。
- 结论拆分：必须区分“静态文件覆盖”“当前会话按规则手动执行”“新会话真实触发已验证/未验证”；不得把静态覆盖写成真实触发成功。

### 步骤 ⑥ 部署与发布验证

部署不是核心流程的前置依赖；它是目标运行时的适配步骤。先完成结构与行为验证，再按环境部署。

必做：
- 运行当前仓库验证脚本或目标环境等价验证。
- 做名称一致性检查：目录名、SKILL.md `name`、接口声明和公开入口一致。
- 做结构一致性审计：新建 skill 或批量修改后读取 `references/structural-audit-methodology.md`。
- 按目标项目的发布规则更新公开说明、安装入口和变更记录；孵化中产物不进入默认公开入口。

按需：
- 同步到当前 AI 工具的 skill 目录。
- 创建本地同步脚本；脚本含本机路径时必须保持 ignored，不作为通用发布产物。
- 同步后做 checksum 或等价内容比对；只运行 rsync/cp 不等于同步成功。

## 不做什么

- 不挖掘历史对话文件
- 不做通用的 skill 创建教学
- 不把一切都变成 skill — 4 层验证不通过就不转化
- 不修改非 skill 相关的项目文件
- 不依赖特定工具的笔记系统 — 「待观察」方法论记录在输出报告中，而非工具特定的笔记目录
- 不保留会暴露用户隐私、私有路径、具体来源链路或未授权项目名的来源描述；默认抽象化
