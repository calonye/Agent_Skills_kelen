# 宿主交互能力适配协议

## 适用条件

新建或迭代的 skill 存在以下任一行为时必须应用：
- 询问会改变行动边界的澄清问题。
- 请求授权执行不可逆、隐私或存储动作。
- 要求用户从候选方案中裁定方向。

## 能力抽象

skill 依赖的是“交互式提问或选择能力”，而不是某一个固定工具名称。能力至少区分：
- `short_text`：简短文本回答。
- `single_choice`：互斥选择。
- `multi_select`：可选多个项。
- `question_capacity`：一次请求支持的问题数量。
- `exposure`：本轮工具目录或宿主接口是否暴露候选原生能力。
- `invocation_result`：候选能力被实际调用后的成功、拒绝、不可用或题型不支持证据。

## 调用顺序

1. 确认本轮是否真的存在 P0 澄清、授权或裁定问题；无则不提问。
2. 查看本轮工具目录或宿主接口暴露的原生交互候选及题型能力。
3. 已暴露满足题型和问题数量的原生交互候选 → 必须先实际调用；成功呈现交互后才能标记 `interaction_mode: native_tool`。
4. 构造选项时，每个选项必须包含一句核心逻辑理由或取舍影响；需要 AI 倾向时必须标注推荐项。
5. 单选题只标 1 个推荐项；多选题可标推荐组合，并说明组合理由。证据不足时不强行推荐，改为说明缺口。
6. 候选未暴露，或实际调用返回不可用、拒绝、题型/题量不支持等证据 → 只输出一个文本降级请求，标记 `interaction_mode: text_fallback`、`native_tool_candidate`、`native_tool_status`、`fallback_reason` 与 `capability_evidence`。
7. 提问后停止后续写入或不可逆动作，等待用户答复。

## 边界

- 不得把 Markdown 中的选项列表宣称为弹窗工具调用成功。
- 不得为了使用原生工具而把多选问题错误改为互斥选择。
- 不得输出没有理由的裸选项；不得把多个互斥项同时标成单选推荐。
- 不得把宿主特定工具名写成目标 skill 的硬依赖；工具名只可作为适配能力示例或接口声明中的可选能力。
- 不得根据权限等级或未经实际调用核验的模式判断，预先推断原生交互候选不可用。
- 执行访问权限和原生交互能力分别判定：文件或命令权限开放，不替代原生控件的实际调用验证。
- 用户已经给出完整裁定后，不重复发问。

## 最小验证

- 正例：宿主提供匹配题型的交互工具，skill 需要用户选方案 → 应实际调用原生工具。
- 降级例：宿主未暴露交互候选，或候选真实调用被拒绝/返回不可用 → 输出一次文本请求并保留运行证据。
- 隔离例：执行访问权限变化不得直接改变原生交互裁定；交互能力必须按暴露与实际调用结果独立验证。
- 多选例：题目需要多选但工具只支持互斥选择 → 不伪装支持，使用文本降级或支持多选的等价能力。
- 推荐例：存在多个裁定选项 → 每项给一句理由；推荐项标注“推荐”，并说明推荐来自证据强度、风险和复验成本。
- 负例：不存在 P0 缺口 → 不调用工具，不制造确认步骤。
- 记录项：`interaction_mode`、题型、问题数量、`native_tool_candidate`、`native_tool_status`、`fallback_reason`、`capability_evidence`、是否等待回答、真实会话是否复验。
