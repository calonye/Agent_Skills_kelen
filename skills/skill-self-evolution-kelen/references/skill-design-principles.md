# Skill 设计原则 / Skill Design Principles

> 本文件是 skill-self-evolution-kelen 转化新 skill 时的强制参考。无论在什么 AI 工具或环境中，
> 产出的 skill 都必须遵循以下原则。

## 格式规范

- SKILL.md 主文件 ≤ 500 行，长内容拆到 `references/`
- 列表项间无空行，同一文件内连续空行不超过 1 个
- 符号替代冗余词（`→` 代替「然后」「流转到」）
- 禁用表格，优先使用自然语言列表
- 避免非必要加粗/特殊字符/空行
- 优先级：规则目的（逻辑完整性）> 模型理解效率 > Token 效率 > 人类可读性

## Frontmatter 规范

```yaml
---
name: <skill-name>
description: >-
  <功能描述>。
  触发场景（用户口语）：
  「<口语触发词1>」「<口语触发词2>」
  触发场景（AI 自我思考）：
  「<推理触发模式1>」「<推理触发模式2>」
  关键词：<关键词1>、<关键词2>。
metadata:
  author: kelen
  version: <版本号>
---
```

必填字段：`name`、`description`、`metadata.author`、`metadata.version`
命名规则由目标运行时或目标仓库约定决定；`-kelen` 是本仓库默认水印，不是跨环境强制后缀。

## 触发词覆盖

### 两层路由机制

Skill 触发依赖两层协作，缺一不可：

- **发现层（description 字段）**：当 AI 已经决定要搜索 skill 时，description 字段决定语义匹配结果。写得再好，如果触发层没有启动搜索动作，description 永远不会被读取。
- **触发层（宿主环境的路由规则）**：决定 AI 是否启动 skill 搜索。上下文路由是触发层的核心——基于对话状态主动触发，而非依赖用户显式指令。

两层断裂的典型症状：skill 文件存在且 description 完善，但整个对话过程中从未被调用。根因通常是触发层缺失或规则中的名称与 skill 目录名不一致。

### 内容要求

- 必须同时覆盖「用户口语触发」和「AI 推理触发」两个维度
- 用户口语触发：必须包含自然口语短句，不只写专业术语；覆盖请求式、疑问式、焦虑式和目标式表达
- 推理触发：AI 在推理过程中识别到需要使用此 skill 的场景
- 发现层关键词：补充中文核心词、常见英文词、同义词和输出物关键词，但关键词不能替代自然短句
- 误触发边界：列出近邻流程和负例，说明相似请求何时不使用本 skill
- 目标：不仅用户明确发出指令时触发，AI 自身推理时也能因语义匹配自动触发
- 详细矩阵见 `references/trigger-coverage-matrix.md`

## 内容净化

### 禁止出现

- **来源叙事**：「从 XX 对话中提炼」「这个设计是我在做 XX 的时候想到的」
- **非权威引用**：「遵循 XX 规范」（除非 XX 已是行业标准）
- **维护说明**：「某工具侧维护」「某运行时侧维护」「按需读取」
- **无实际规则意义的描述**：仅描述「从哪来」「谁维护」的注释

### 允许保留

- 实际规则和约束条件
- 流程步骤和输出格式
- 触发条件和关键词
- 与其他 skill 的功能边界说明（如「核心区别」对比段落）

### 权重判断

引用、参考、具体来源 → 低权重。若经用户确认需要保留：
- 放在文件末尾或脚注位置
- 作为注释类型出现
- 不出现在 description 或核心流程段落中

## 明确判断不干扰原则

- **高置信度判断**（如移除明显的来源叙事）→ 直接执行，不征求用户确认
- **模糊/有争议判断**（如某个引用是否属于行业标准）→ 必须征求用户意见
- 目的：避免上下文被确认环节污染，同时保留关键决策的用户控制权

## 规则与说明分离

- **SKILL.md**：给 AI 执行的规则和流程
- **README.md**（如有）：给人类阅读的说明、设计背景、版本历史
- 两者内容不混放

## 目录结构

### 示例驱动准备

创建或重构 skill 前，先用 2-3 个具体使用例确认：
- 真实用户会怎么触发。
- 用户会提供什么输入。
- skill 应交付什么输出。
- 哪些近邻请求不应该触发。

若示例不足且会影响边界，先澄清；若用户目标已足够明确，可以生成候选例让用户确认。

### 通用核心结构

跨运行时可迁移的核心结构只要求：
- `SKILL.md`：主文件，含 frontmatter、路由描述、最小流程和输出契约。
- `references/`：按需加载的判据、案例、协议或领域知识。

### 资源边界裁定

只添加能降低当前歧义、执行负担、路由风险、验证风险或维护风险的资源：
- `references/`：承载按需读取的长规则、判据、案例或领域知识。
- `scripts/`：承载确定性、重复、易错且比文字更可靠的逻辑。
- `assets/`：承载输出会直接使用的模板、静态资源或样例资产。
- `evals/`、`reports/`：仅在路由、质量或发布结论需要可复验证据时创建。

禁止为了显得完整而创建空目录、装饰性报告、未被 `SKILL.md` 引用的资源，或尚无真实变体支撑的宽泛配置。

`SKILL.md` 只保留触发面、核心执行骨架、输出契约和必要分支；长解释、案例和环境差异进入按需 reference。

### 执行自由度裁定

按任务脆弱度选择表达形式：
- 高自由度：方案、审查、判断、发散或需要语境取舍的任务 → 写规则、边界、反例和输出契约。
- 中自由度：步骤稳定但仍需上下文判断的任务 → 写流程模板、检查清单和可替换参数。
- 低自由度：重复、易错、确定性或格式严格的任务 → 优先脚本、固定模板或强验证门禁。

裁定原则：确定性越高，越应减少模型自由发挥；语境依赖越高，越应保留判断空间并加强边界和复验。

### 脚本适配裁定

当质量要求具备重复性、确定性、格式严格、可自动验证或容易被模型遗漏时，优先考虑 `scripts/`、固定模板或强门禁：
- 应创建脚本：结构一致性、必备短语、命名一致性、禁用内容、长度边界、发布入口同步、可机械复验的 regression case。
- 不应脚本化：需要语境判断、价值裁定、反方质疑、用户取舍或跨领域抽象的内容。
- 脚本语言选择：优先复用仓库既有工具链；若是跨环境长期维护、性能敏感、并发/文件遍历密集或需要稳定分发的脚本，优先 Rust；其次选择目标环境已稳定具备的高性能脚本/运行时；一次性低风险校验可用现有 shell/Ruby/Python/Bun 等最小依赖实现。
- 不创建脚本时说明原因，至少说明为什么文字规则、检查清单或人工复验已经足够。

### 环境适配层

以下文件属于目标运行时或项目发布约定，不是所有环境的硬性要求：
- 接口声明文件：目标工具不读取该文件时，可换成等价 manifest 或省略。
- `scripts/`：仅在确定性验证或重复执行值得脚本化时创建。
- `evals/`、`reports/`：仅在需要行为评估、发布证据或团队复用时创建。
- 本地部署脚本：含本机路径时必须排除在通用发布产物之外。
- 人类说明文档：承载使用入口、版本背景或研发记录；不承载 AI 执行规则。

```
<skill-name>/
├── SKILL.md              # 主文件（路由 + 流程骨架，≤ 500 行）
├── agents/
│   └── interface.yaml    # 接口声明（按目标环境规范裁定）
├── references/           # 详解、判据、案例（按需加载）
│   ├── <topic>.md
│   └── adapters/         # 适配案例（环境相关时使用）
└── README.md             # 人类说明（可选，不给 AI 读取）
```

## 渐进式披露

- **第 1 层**（metadata）：name + description，始终在上下文中（~100 tokens）
- **第 2 层**（SKILL.md body）：skill 触发时加载（≤ 500 行）
- **第 3 层**（references/）：按需加载（无限制）

## 验证原则

Skill 设计和部署后必须验证，否则等于没做：

1. **改了规则 ≠ 改了行为**：规则写进文件后，必须在新环境/session 中验证行为是否变化，否则等于没改。
2. **同步后必须做一致性检查**：自动同步脚本跑过了不等于同步成功。同步后必须 checksum 比对两端内容一致。
3. **命名变更后做全链条搜索一致性验证**：重命名 skill 后，从 `name` 字段 → 目录名 → 接口声明 → 路由规则 → 公开触发词，全链条必须一致。用结构化搜索确认旧名无遗漏。
4. **批量创建后做结构一致性审计**：创建新 skill 后，横向对比目录结构、接口声明、脚本和参考文件等结构特征与已有同类产物是否一致。内容验证检查"写对了没有"，结构审计检查"长对了没有"。详见 `references/structural-audit-methodology.md`。
5. **行为验证先于完成声明**：至少用正例、近邻例和负例检查触发边界；低风险改动可人工验证，高风险或生产级 skill 才需要 with-skill / baseline 对照。
6. **前向测试门槛**：复杂、高风险或公开复用的 skill，应在新上下文或独立执行环境中用少提示测试；测试输入只给任务和必要材料，不泄露预期答案、修复意图或作者结论。
7. **发布入口验证**：公开说明、安装入口、变更记录、触发词和目录树必须与实际公开 skill 一致；孵化中产物不进入默认公开入口。
8. **交互能力验证**：skill 需要澄清、授权或裁定选择时，宿主具备适配题型的原生交互能力就必须实际调用；仅当能力缺失或受限时使用文本降级，并记录原因。
9. **运行产物隔离验证**：skill 会创建会话记录、附件、执行日志或任务结果时，公共规则目录只保留协议与模板；真实运行数据进入目标项目允许的私有记录区域。
10. **自动演化禁令**：skill 的业务流程可以报告改进候选，但不得自行改写执行规则或将真实项目历史追加到公共 skill 包。

## 交叉引用规范

每个 skill 必须完全独立可用，交叉引用仅作可选辅助增强，不得影响 skill 的独立运行能力。

- 独立可用原则：移除另一个 skill，本 skill 仍能完整执行核心流程
- 「可选搭配」标注：SKILL.md 中出现的其他 skill 名称前加「可选」标记；引用段落标题改为「可选搭配」
- 禁止依赖性语言：不得出现「必须先执行」「闭环」「前置条件」等暗示依赖关系的措辞
- 边界说明：在「不做什么」段落中标注功能边界时，仅说明用什么替代，不得要求必须使用
- 交叉触发：「当 X 时，可（可选）搭配 Y 做 Z」而非「做完 X 后，用 Y 做 Z」
- 外部资料、具体来源、对照规范和工具名只能沉淀到研发文档；skill 执行规则只保留可独立运行的功能约束。
- 宿主能力名称可在接口适配与能力判定中作为必要技术标识出现，但通用流程不得依赖单一宿主或假定其一定存在。
