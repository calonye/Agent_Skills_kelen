# 抽象案例：自我进化的三个场景

## 场景 1：交付可用性审计方法

### 识别
在多轮「假装新人接手」的审计中，发现了一个可重复的模式：模拟 clone → setup → 日常流程，逐步找出卡点。

### 4 层验证

- 必要性：不固化 → 下个项目不会主动做新人模拟 → 通过。
- 唯一性：与代码审查（面向代码）本质不同，本 skill 面向系统可用性 → 通过。
- 可结构化：有清晰的步骤 + 清单 + 子模式 → 通过。
- 投入产出比：轻量级，任何项目交付前可复用 → 通过。

### 结果
建议沉淀为独立交付审计 skill，或合入已有交付审计流程。

## 场景 2：决策前自我反驳方法

### 识别
对话中反复出现「先反驳自己的方案」的需求，形成了一个结构化的自我反驳协议。

### 4 层验证

- 必要性：不固化 → AI 决策前不会自我反驳 → 通过。
- 唯一性：与代码审查（外向）、发散探索（创意）都不同，本 skill 是内向收敛 → 通过。
- 可结构化：五步协议 + 第一性原理判据链 → 通过。
- 投入产出比：轻量级，任何重要决策前可复用 → 通过。

### 结果
建议沉淀为独立决策自审 skill，或合入已有决策审查流程。

## 场景 3：会话内方法论固化

### 识别
深度对话中反复出现“把新掌握的方法论沉淀下来”的需求，形成了五段自我进化循环。

### 4 层验证

- 必要性：不固化 → 领悟随 session 消亡 → 通过。
- 唯一性：与事后挖掘历史、被动记录知识、按明确需求创建 skill 都不同 → 通过。
- 可结构化：五段协议，明确的输入/输出和验证方式 → 通过。
- 投入产出比：轻量级，每次深度对话结束时可复用 → 通过。

### 结果
建议创建或迭代一个会话内方法论固化 skill。示例只保留可复用判据，不记录具体对话来源或个人路径。
