# 结构一致性审计方法论 / Structural Consistency Audit

## 问题定义

在批量创建同类产物时，AI 容易陷入**内容焦点盲区**：全部注意力集中在单个文件的内容验证上，完全忽略新产物与已有产物之间的结构一致性。

典型症状：创建了新模块，检查了主说明和参考文件的内容，却漏掉接口声明过薄、脚本缺失、目录结构和同类产物不一致等结构问题。

## 核心原则

**每次创建批量新产物后，必须在内容验证之上增加一层结构一致性审计。**

内容验证检查的是"写对了没有"——结构审计检查的是"长对了没有"。

## 三步审计流程

### 步骤 A：提取基线

从已有产物（已知正确的参照物）中提取结构基准：

- 文件类型清单：列出所有文件扩展名和文件名模式
- 目录结构：列出所有子目录及其层级
- 关键文件的结构特征：YAML 字段数、脚本头部格式、特定段落存在性

无需读取文件内容，通过 shell 提取结构信息：

```bash
# 提取目录结构
find skills/reference-skill/ -type f | sort

# 提取 interface.yaml 关键字段数
rg -c '^name:|^inputs:|^outputs:|^tools_required:|^constraints:' \
  skills/reference-skill/agents/interface.yaml

# 提取文件类型分布
find skills/reference-skill/ -type f | sed 's/.*\.//' | sort | uniq -c
```

### 步骤 B：交叉对比

将新产物的结构特征与基线对比：

- 目录结构：用 `diff <(find base/ -type f | sed 's/base/new/' | sort) <(find new/ -type f | sort)` 检查是否存在缺失或多余文件。
- 文件数量：按扩展名和关键文件名统计，每类文件的计数应能解释。
- 接口声明：字段数量和字段名称应与基线一致；差异必须有明确理由。
- 部署脚本：检查脚本是否存在、格式是否一致、是否被正确归类为发布产物或本地产物。
- Agent 接口声明：检查接口目录是否包含目标运行时需要的必要文件。

### 步骤 C：差异裁决

对发现的差异逐项裁决：

- **合理差异**：新产物的独特功能需要不同的结构。记录理由。
- **遗漏**：基线有、新产物无。这是盲区产物，立即补充。
- **多余**：新产物有、基线无。确认必要性后决定保留或移除。

## 适用范围

- 批量创建 skill/droid/rule 等模块化产物
- 批量创建配置文件或模板
- 任何存在多个同类产物的项目
- 接手他人项目时的结构完整性检查

## 与内容审计的关系

结构审计和内容审计是正交的：

- 结构审计：检查产物间的横向一致性（文件类型、字段、脚本）
- 内容审计：检查单个产物内的纵向正确性（引用、格式、规范）

两者缺一不可。结构审计应在内容审计之前或同时进行。

## 触发时机

- 创建新 skill 后的交付检查
- 批量修改多个 skill 后的提交前检查
- 项目交付/交接前的最终完整性检查
- 新成员加入时的项目结构学习验证
